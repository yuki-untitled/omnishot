# バグ修正: ストリーム接続が一時的に切断されただけで、自動撮影セッション全体が停止する

## Issue
#LOCAL-017

## 不具合現象と再現手順（Why）
### 発生している現象
自動撮影中（[screenshot-capture.md](../screenshot-capture.md)）、iOS/Androidいずれかの端末とのストリーム接続が一時的に切断されると、再接続を試みることなく即座に自動撮影セッション全体が停止する。端末は実際には接続されたままでも、ユーザーは手動で「自動撮影」を押し直す必要がある。

### 再現手順
1. 端末（iOSまたはAndroid）を接続し、「自動撮影」で撮影を開始する
2. 撮影中にストリーム接続が一時的に切断される（実機では `IncompleteRead` 等のエラーで発生することを確認済み。USB/Wi-Fi環境によっては再現しないこともある）
3. 期待値・実際の差異
   - 期待値: 端末が実際には接続されたままであれば、自動で再接続し、撮影が継続されること
   - 実際: 切断を検知した時点で即座に撮影が停止し、ユーザーへは「⚠️ ストリームが切断されました」等のエラーのみが表示される

## 修正内容（What）
### 根本原因
1. ストリーム接続（iOSの常時ストリーミング、Androidの`screencap`実行）が一時的に不安定になることがあるが、切断を検知した際の処理が「即座にセッション全体を停止する」のみで、再接続を試みる仕組みがなかった。
2. iOSストリームの起動処理が、実際にサーバーが起動できたかを確認せず、固定で1.5秒待つだけだった。起動が遅い場合は接続確立前にフレーム受信を試みてしまい、逆に不要に待ちすぎることもあった。
3. iOSストリームを起動する `go-ios` プロセスの標準エラー出力を破棄しており、起動・切断に失敗した実際の原因（アプリ側からは見えないエラーメッセージ）を確認できなかった。
4. プロセスの終了処理（`cleanup_all_processes`）が `terminate()` のみで、応答がない場合はエラーを握りつぶして諦めていた。終了し切れなかったプロセスがポートを握ったまま残ると、次回のストリーム起動に影響しうる。

### 修正方針
- ストリーム接続が切断された場合、最大2回まで自動で再接続を試みてから撮影を継続する。
- 再接続を試みている間も、ユーザーが「停止」を押した場合はその時点で撮影を終了する。
- 再接続時は、切断前の変化検知の判定状態（直前のフレームとの差分・移動平均）を持ち越さず、新しい接続からやり直す。
- 端末が実際に切断されている場合（再接続時の端末解決に失敗する場合）は、再接続の残り回数を待たずにその場でエラーを表示して停止する。
- 再接続を2回試みても接続できない場合は、従来通りエラーを表示して自動撮影を停止する。
- iOSストリームの起動待ちを、固定時間の`sleep`から、実際にポートが接続を受け付けるようになるまでのポーリング（最大5秒、プロセスが先に終了した場合は打ち切り）に変更する。
- `go-ios`プロセスの標準エラー出力を監視し、起動・接続の失敗原因を把握できるようにする（手動撮影の単発コマンド側も同様）。ただし、Live Logsを埋めないよう、この出力そのものをログへは表示しない。
- プロセスの終了処理で、`terminate()`が効かない場合は`kill()`で確実に終了させる。
- `go-ios`の標準エラー出力のうち、JSON形式で`level`が`fatal`または`error`の行があれば、その`msg`を切断時のユーザー向けエラーメッセージに反映する（HTTP接続断のメッセージだけでは分からない、実際の失敗理由を見せるため）。これが、上記の失敗原因をユーザーに見せる唯一の手段になる。

## 受入基準（再発防止・回帰テスト）
1. **一時的な切断からの復帰**: 撮影中にストリーム接続が切断されても、端末が実際には接続されたままであれば、自動で再接続され、撮影が継続されること（ログに再接続した旨が表示されること）。
2. **再接続中の停止操作**: 再接続を試みている間に「停止」を押すと、その時点で撮影が終了し、それ以上再接続を試みないこと。
3. **端末が本当に切断された場合**: 再接続を試みた時点で端末が実際に接続されていなければ、残りの再接続回数を待たずに「選択した端末が接続されていません」等のメッセージが表示され、撮影が停止すること。
4. **再接続の上限**: 切断が2回の再接続後も解消しない場合、従来通りエラーメッセージが表示され、自動撮影が停止すること。
5. **回帰（正常系）**: 切断が発生しない通常の撮影では、静的モード・動的モードの撮影タイミング、保存されるファイル名の形式が、従来どおり動作すること（[screenshot-capture.md](../screenshot-capture.md) の受入基準）。
6. **回帰（手動撮影・セッショングルーピング）**: 再接続をまたいでも、手動撮影（[manual-capture.md](../manual-capture.md)）・撮影セッションのグルーピング（[session-grouping.md](../session-grouping.md)）が従来どおり動作すること（再接続はセッションを区切らない）。
7. **起動待ちの見直し**: iOSストリームの起動時、ポートが受け付け可能になり次第（1.5秒未満でも）撮影が始まること。起動に失敗した場合は、5秒程度でタイムアウトしエラーが表示されること。
8. **手動撮影の失敗原因**: 手動撮影（iOS/Android）が失敗した際、`go-ios`/`adb`からのエラー内容がログに表示されること（原因調査ができること）。
9. **切断理由の反映**: `go-ios`が`fatal`/`error`レベルのログを出して切断した場合、その内容（例:「Screenshot failedTakeScreenshot: Timed out waiting for response...」）が、ユーザー向けの停止メッセージにも反映されること。
10. **Live Logsの静粛性**: 通常の起動・撮影では、`go-ios`の標準エラー出力そのもの（`⚙️ [go-ios] ...`形式の行）がLive Logsに表示されないこと。

## 調査メモ
- 追加したログ転送により、実機で以下の`go-ios`側のログを確認できた。
  ```
  {"channel_id":"com.apple.instruments.server.services.screenshot","error":"Timed out waiting for response for message:1 channel:1","level":"info","methodselector":"takeScreenshot","msg":"failed starting invoking method"}
  {"level":"fatal","msg":"Screenshot failedTakeScreenshot: Timed out waiting for response for message:1 channel:1"}
  ```
  これは、`go-ios`が端末側の`com.apple.instruments.server.services.screenshot`（Instruments系のDTXサービス）へ`takeScreenshot`を要求したが、端末からの応答が一定時間なく、`go-ios`プロセス自体が`fatal`終了しているというログである。Python側で見えていた「iOS device disconnected: Remote end closed connection without response」は、この`go-ios`プロセスの異常終了に伴ってHTTP接続が切れた結果であり、Python側のバグではなかった。
  - 1回目の切断までは約5秒（`go-ios`内部のタイムアウトと見られる）。再接続した2回目は、同じ症状がより短時間（約1秒）で再発しており、端末側のInstruments関連サービスの状態が引き続き悪化している可能性がある。
  - `com.apple.instruments.server.services.screenshot`はInstruments系のサービスであり、一般に「デベロッパーモード」が有効であることや、端末に対応する開発者ディスクイメージ（Developer Disk Image）がマウントされていることを要求する。go-iosの最近のリリースでは「instruments/devmodeが未対応の端末で失敗する理由をより分かりやすくする」改善が入っているとの情報があり（検索結果からの間接的な情報で、本リポジトリのバンドル版v1.0.213での対応状況は未確認）、この種の要求が満たされていないと同様の症状になりうる。
  - `com.apple.instruments.server.services.coreprofilesessiontap`等、他のDTX系サービスでもiOS 14以降でメッセージのパースエラーを致命的に扱ってしまう既知の不安定さが報告されている（[danielpaulus/go-ios#661](https://github.com/danielpaulus/go-ios/issues/661)）。スクリーンショットのストリーミングも同系統のDTX接続を使っているとみられ、同種の不安定さの影響を受けている可能性がある。
- アプリ側（本リポジトリ）で確認・修正できたのは、上記の「根本原因」1〜4、および切断理由の可視化。`com.apple.instruments.server.services.screenshot`が応答しない根本原因（端末側のデベロッパーモード設定・開発者ディスクイメージの状態・go-iosのバージョン起因の問題である可能性）は、実機・go-iosのバージョンに依存するため、コードの修正だけでは解消を保証できない。次に発生した際は、ログに表示される`go-ios`からのメッセージを手がかりに、端末側の設定（デベロッパーモードがオンか、コンピュータを信頼済みか）を確認する必要がある。

## 変更理由
- issue #LOCAL-017: 実機で、自動撮影開始直後にiOSストリームが `IncompleteRead` で切断され、撮影セッション全体が停止する不具合を確認したため新規作成。ストリーム接続の一時的な不安定さは既知の制限（[screenshot-capture.md](../screenshot-capture.md)の既知の制限事項）だが、切断のたびにセッション全体を止めるのではなく、まず自動で再接続を試みる方針に修正した。
- issue #LOCAL-017: 「なぜ接続が不安定になるのか」の原因調査依頼を受け、コード全体を読み合わせて追加の原因（起動待ちが固定時間頼みだったこと、go-iosのエラー出力を破棄していたこと、プロセス終了処理がkillにエスカレーションしないこと）を特定し、修正・受入基準に反映。go-ios自体の接続安定性はブラックボックスで制御できないため、「調査メモ」に確認できた範囲・できなかった範囲を明記した。
- issue #LOCAL-017: ログ転送の追加後、実機で`go-ios`の実際の失敗理由（`com.apple.instruments.server.services.screenshot`への`takeScreenshot`要求がタイムアウトし、`go-ios`プロセスがfatal終了）を確認できた。ユーザー向けの切断メッセージにこの理由を反映する対応を追加し、調査メモ・受入基準を更新した。根本原因（端末側のInstruments関連サービスが応答しない理由）はアプリのコード修正だけでは解消を保証できないため、その旨を明記した。
- issue #LOCAL-017: 実機で接続が安定するようになったことを確認。あわせて、`go-ios`の標準エラー出力をLive Logsにそのまま表示していたのはノイズが多いという指摘を受け、失敗原因の把握（`self.last_stream_error`への保持）は残したまま、通常のログへの転送は取りやめた。受入基準を「ログに表示される」から「ユーザー向けメッセージに反映される」「Live Logsを埋めない」に修正。
