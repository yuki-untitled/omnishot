# バグ修正: 動的モードで、ストリームの新しいフレームが届いていないのに「静止」と誤判定され、操作中でも撮影されてしまう

## Issue
#LOCAL-004

## 不具合現象と再現手順（Why）
### 発生している現象
動的モード（[screenshot-capture.md](../screenshot-capture.md)）で、チェック間隔を短く（例: 0.1秒）設定すると、実際には端末の画面を操作し続けている最中にもかかわらず「静止」と判定され、撮影が実行されてしまう。

原因は、キャプチャループ（[omnishot/capture.py](../../../omnishot/capture.py)の`auto_capture_loop`）が、受信スレッド（[omnishot/stream_receivers.py](../../../omnishot/stream_receivers.py)の`iOSStreamReceiver`/`AndroidScreencapReceiver`）から`latest_frame`を毎ポーリングで読み取るだけで、そのフレームが前回のポーリング時から実際に更新されたものかどうかを確認していなかったこと。設定したチェック間隔が、ストリーム側の実際のフレーム配信間隔より短い場合、複数回のポーリングにわたって同一のフレームを読み続けることになる。「変化あり」を検知した直後は比較基準フレーム（`state.last_frame_data`）がそのフレームに更新されるため、次のポーリングで同じフレーム（更新されていないフレーム）を読むと差分が0になり「変化なし（静止）」と誤判定される。これが判定回数分連続すると、実際には操作が続いているにもかかわらず撮影が確定してしまう。

### 再現手順
1. iOS端末を接続し、動的モードでチェック間隔0.1秒、判定回数1〜3程度に設定して自動撮影を開始する
2. 端末の画面を継続的に操作する（スクロール、タップによる画面遷移など）
3. ログを確認する
   - 期待値: 操作を続けている間は「🎬 画面動作中...」が継続し、実際に操作をやめて静止するまで撮影されない
   - 実際: 操作を継続しているにもかかわらず、短時間で「📊 静止確認」が判定回数分進み、撮影が実行される

## 修正内容（What）
### 根本原因
- キャプチャループが、受信フレームの「新規性（前回ポーリング時から更新されたかどうか）」を確認せず、毎ポーリングで無条件に変化判定へ回していた
- 特にiOS側は、Appleのスクリーンショット取得サービス経由でのストリーム配信レートが、設定可能なチェック間隔の下限（0.1秒）よりも遅くなる場合があり、この場合ほぼ確実に同一フレームの重複読み取りが発生する

### 修正方針
- 受信スレッド側で、フレームが更新されるたびに増加する識別子を保持する
- キャプチャループ側は、前回処理したフレームと識別子が同じ（＝ストリームからまだ新しいフレームが届いていない）場合、そのポーリングでは変化判定を行わず、次のポーリングまで待つ
- これにより、「フレームが更新されていない」ことと「フレームは更新されたが内容が変化していない（本当の静止）」を区別できるようにする

## 受入基準
1. **重複フレームの除外**: ストリームから新しいフレームが届いていないポーリングでは、変化検知の判定（「変化あり」「変化なし」のいずれの判定も）が行われないこと。
2. **操作中の誤検知防止**: 動的モードで端末を継続的に操作している間、ストリームの配信間隔がチェック間隔より遅い場合でも、操作が実際に止まるまで撮影されないこと。
3. **回帰（本当の静止時の撮影）**: 端末の画面操作を実際に止めた場合、設定した判定回数の連続した「変化なし」判定を経て、従来通り撮影が行われること。
4. **回帰（静的モード）**: 静的モードの撮影タイミング（既存の受入基準、[screenshot-capture.md](../screenshot-capture.md)参照）に影響がないこと。
